# ADR-0012: Архитектура Telegram-подсистемы

- **Статус:** Принято
- **Дата:** 2026-07-31

## Контекст

Telegram — первый реальный канал доставки и первая «живая» функция продукта.
Подсистема рассчитывается на коммерческое использование сразу: ретраи, лимиты,
очередь, безопасность секретов — чтобы при росте (мониторинг грузов будет
слать уведомления постоянно) её не пришлось переписывать.

## Решение

1. **Порт `TelegramApi` в ядре + фабрика.** `TelegramService` (application)
   не может импортировать httpx-клиент (контракт «services → только core»),
   поэтому зависит от порта; `TelegramClient` (infrastructure) реализует его.
   Фабрика позволяет пересоздавать клиент при смене токена и подменять в тестах.
2. **Один `httpx.AsyncClient` на клиент** (не на запрос): пул соединений,
   таймауты connect 5 / read 10 / write 10 / pool 5, закрытие через `aclose()`.
3. **RetryPolicy:** 429 → пауза из `retry_after` ответа; 5xx и сеть — до 3
   попыток с экспонентой и джиттером; 400/401/403/404 не повторяются.
   404 Bot API означает несуществующего бота → маппится в `TelegramAuthError`.
4. **Машина состояний** DISCONNECTED → CONNECTING → CONNECTED/ERROR в сервисе,
   каждое изменение — событие `TelegramStatusChanged`; успешная отправка
   «лечит» состояние ERROR.
5. **Очередь отправки:** `send_notification()` кладёт в `asyncio.Queue` и
   возвращается мгновенно; фоновый воркер (ленивый старт — петля qasync
   появится на UI-этапе) отправляет через RateLimiter (интервал 1 с — лимит
   Telegram на чат) и публикует `NotificationDispatched`/`NotificationFailed`.
6. **Сервис не собирает строки:** порт `NotificationFormatter` (generic, не
   телеграм-специфичный — переиспользуют будущие каналы); реализация
   `TelegramNotificationFormatter` + `TelegramMessageBuilder` (fluent, HTML,
   автоэкранирование & < > ") — новые виды сообщений (груз, отчёт,
   AI-рекомендация) добавляются методами форматтера.
7. **Безопасность секретов:** токен живёт в URL Bot API, поэтому (а) логгеры
   httpx/httpcore приглушены до WARNING (их INFO печатает полный URL);
   (б) все сообщения ошибок санитизируются (токен → `***TOKEN***`);
   (в) сервис не логирует ни токен, ни chat_id. Покрыто тестами.
8. **Токен по требованию:** сервис получает `token_provider`/`chat_id_provider`
   (bootstrap подставляет методы SettingsService) — Keychain-диалог не
   выскакивает на старте приложения, токен читается в момент отправки.
9. **`verify()`** — трёхшаговый сценарий на временном клиенте (значения из
   формы, основное подключение не трогается): getMe → getChat → тестовое
   сообщение; максимально подробный `VerificationResult` (какой шаг упал,
   человекочитаемая причина, @username бота, название чата, подсказка про
   Start при «chat not found»).

## Альтернативы

- Готовые библиотеки (python-telegram-bot, aiogram) — тянут своё управление
  циклом/диспетчеризацию под ботов-серверы; нам нужен тонкий исходящий клиент
  на 5 методов, свой контроль ретраев и секретов.
- Отправка без очереди («fire and forget» задачами) — параллельные задачи
  пробивают лимит Telegram и теряют порядок; очередь + лимитер решают оба вопроса.

## Последствия

(+) Подсистема готова к этапу 3.5 (NotificationService вызовет
`send_notification` без изменений) и к мониторингу (v0.2).
(−) Компромиссы: sendPhoto/sendDocument принимают file_id/URL (multipart-загрузка
локальных файлов — при первой реальной необходимости); публикация
NotificationDispatched/Failed пока в TelegramService — на этапе 3.5 переедет
в NotificationService (агрегация по каналам); реальная проверка с ботом
выполняется скриптом `scripts/telegram_smoke.py` на машине владельца
(секреты в репозиторий и чат не передаются).
