# ADR-0025: Production Telegram — бот, шаблоны, inline-кнопки

- **Статус:** Принято
- **Дата:** 2026-07-31

## Контекст

Telegram был каналом доставки уведомлений (ADR-0012/0013). Для эксплуатации
нужен двусторонний бот: команды пользователя, красивые сообщения, кнопки
действий — не ломая Clean Architecture: Telegram остаётся одним из каналов
Notification Center, не знает ни ATI, ни Search Engine.

## Решение

1. **Порт TelegramApi расширен аддитивно**: ``get_updates`` (long polling),
   ``answer_callback_query``, параметр ``buttons`` в ``send_message``; новые
   модели ядра — TelegramUpdate (плоское обновление) и TelegramButton
   (url ИЛИ callback_data). Существующие вызовы совместимы (default ``()``).
2. **TelegramCommandRouter** (`services/telegram/router.py`) — словарь
   «команда → обработчик»: никаких if-else в клиенте; обработчики
   регистрирует composition root; ``commands()`` питает /help, /start и
   список для BotFather; упоминание бота (`/status@bot`) отрезается.
3. **TelegramBotService** (`services/telegram/bot.py`) — long polling поверх
   порта: отвечает ТОЛЬКО настроенному chat_id (чужие чаты игнорируются, их
   идентификаторы не логируются), callback_data валидируется whitelist-
   регэкспом (``details|ignore`` + cargo_id ≤ 48 симв.), сбои поллинга не
   роняют цикл, graceful start/stop (без токена бот честно молчит).
4. **Команды**: /start, /help — из описаний роутера; /status — ATI
   Online/Offline, синхронизация, найденные грузы, лучший груз, Scheduler,
   версия; /report — аналитика Stage 8 (найдено, подходящих, средняя
   прибыль, лучший маршрут, доход, ошибки источников); /settings — read-only
   снапшот (машина, регион, мин. ставка, веса AI Score, источники, каналы);
   **/search — мутация строго через CommandBus** (существующая RunJobNow
   «source:ati») + итог после ``pipeline.wait_idle()``. Чтение (/status,
   /report, /settings) НЕ оборачивается в команды — по ADR-0005 чтение
   выполняется query-методами сервисов; данные собирает composition root,
   тексты — ``infrastructure/telegram/bot_replies`` (правило «внешний вид
   сообщений — в инфраструктуре» сохранено).
5. **Красивые уведомления**: TelegramNotificationFormatter — шаблон по
   категории (🚚 лучший груз, 📦 обновление цены, ⚠️/🟢 источник
   offline/restored, 📊 дневной отчёт, 🚨 ошибки Scheduler/поиска),
   разделитель, HTML-экранирование всех пользовательских данных.
6. **Inline-кнопки** из существующей модели NotificationAction: url-действия
   → url-кнопки («Открыть ATI»), whitelist-действия details/ignore →
   callback-кнопки с cargo_id из payload (невалидный id — кнопка не
   создаётся). «Подробнее» — карточка груза из CargoRepository через
   инжектированный провайдер; «Игнорировать» — груз убирается из
   рекомендаций дашборда через инжектированный sink. Доменная модель
   уведомлений не менялась.
7. **Длинные сообщения** режутся по границам строк (лимит Telegram 4096),
   клавиатура прикрепляется к последнему чанку; 429/5xx/сеть — существующие
   ретраи RetryPolicy клиента.
8. **BotFather** — полный гайд ``docs/telegram-botfather.md``: команды,
   описание, About, privacy, подключение.

## Последствия

(+) Пользователь управляет LogistAI из Telegram: статус, отчёт, ручной
поиск, действия по грузу — при этом Telegram-слой знает только Notification,
порт и инжектированные колбэки (контракты import-linter 7/7). Безопасность
закреплена тестами: токен/chat_id не в логах, callback только по whitelist.
(−) Поллинг и обработчики последовательны (один пользователь — приемлемо;
webhook-режим — при необходимости, за тем же портом); /search блокирует
обработку следующих команд до завершения опроса; изменение настроек из бота
намеренно read-only (мутации настроек — Stage 9.1 в UI).
