# ADR-0011: Архитектура логирования

- **Статус:** Принято
- **Дата:** 2026-07-31

## Контекст

Нужно системное логирование: файл для диагностики, живая лента для будущей
страницы «Логи», ошибки — в статус-бар. При этом UI не должен импортировать
инфраструктуру, а логи не должны зациклиться через шину событий.

## Решение

Stdlib `logging`, один вызов `setup_logging()` в composition root (идемпотентен),
три получателя каждой записи:

1. **RotatingFileHandler** → `~/Library/Logs/LogistAI/app.log`
   (1 МБ × 5 бэкапов; путь — platformdirs).
2. **RingBufferHandler** — последние 2000 записей в памяти; реализует порт
   `LogBuffer` из ядра — страница «Логи» будет читать через порт, не зная
   об инфраструктуре.
3. **EventBusLogHandler** — публикует `LogRecordAdded` для живой ленты.
   Зависит от порта `EventPublisher` (не от `app.buses`) — контракт
   «infrastructure → только core» сохранён. Встроена защита от рекурсии:
   лог → событие → подписчик снова логирует → повторный вход пропускается.

Каждую строку лога в SQLite **не** пишем: журнал событий (HistoryEntry) и
диагностические логи — разные вещи; SQLite-журнал появится на этапе
уведомлений и будет хранить бизнес-события, а не строки логов.

Время в снимках и событиях — UTC из `record.created` (единая шкала с журналом).

## Альтернативы

- structlog/loguru — удобны, но stdlib достаточно, меньше зависимостей;
  формат JSON-логов можно добавить handler'ом позже.
- Все логи в SQLite — шум, разрастание БД, нулевая ценность для диагностики
  относительно файла.
- Qt-сигналы вместо событий — привязали бы инфраструктуру логов к Qt.

## Последствия

(+) UI получает логи через порт; файл ротируется; лента живая; рекурсия
исключена и покрыта тестом; кольцевой буфер не растёт бесконечно.
(−) Буфер живёт в памяти процесса (2000 записей ≈ мегабайты максимум) и
теряется при перезапуске — для истории есть файл.
